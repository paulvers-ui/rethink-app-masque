# Publishing this fork on F-Droid

## GitHub or GitLab?

**Your code stays on GitHub.** F-Droid builds from any git repository;
it doesn't care where it's hosted.

GitLab is needed **only to submit the request**, because `fdroiddata` — the
repository where every app's metadata lives — is at
`gitlab.com/fdroid/fdroiddata`. You need a GitLab account, but nothing more:
you don't have to move, duplicate, or mirror the code.

There are two paths, and both go through GitLab:

| path | your effort | speed |
|---|---|---|
| **Submission Queue** — you open a ticket and the team writes the metadata | low | slow |
| **Merge request** — you write the metadata yourself and propose it | high | much faster |

The second is faster precisely because you take work off the reviewer's plate. If
you pick that one, you're responsible for the metadata being correct.

Details that get an MR rejected if overlooked:

- The MR title must follow the format `New app: <name>`.
- Your `fdroiddata` fork has to be **public** and the branch **unprotected**,
  or they can't rebase before merging.
- Every release needs a **git tag**. If `versionName` is `1.0`, you need a
  tag `v1.0`. Pointing at a branch isn't accepted.
- Don't submit metadata generated by `fdroid import` as-is.

## This app's real problem

F-Droid builds **everything** from source and rejects prebuilt binaries checked
into the repository. There are two here:

| what | where | where it comes from |
|---|---|---|
| `libusque.so` (13 MB) | `app/src/main/jniLibs/arm64-v8a/` | `github.com/paulvers-ui/usque` (fork of diniboy1123/usque, Go, MIT) |
| `firestack.aar` | `app/libs/` | `github.com/paulvers-ui/firestack`, `n2` branch (fork of celzero/firestack, Go, MPL-2.0) |

**Watch out for the firestack branch.** The fork has several historical
branches; only `n2` in `paulvers-ui/firestack` carries the correct API
(`OnQuery(uid, domain *Gostr, qtyp int)`, without the `who` parameter upstream
added and without losing `Gostr`/`Gobyte`). If you ever clean up that repo,
that's the branch to keep.

Both being FOSS with public source is what makes this **possible** at all. If
they were sourceless binaries, there'd be nothing to do here.

The recipe in `com.arcadesignpro.auroravpn.yml` deletes them (`rm:`) and rebuilds
them (`prebuild:`) from `srclibs`. That's the whole trick.

You also have to force `firestackRepo=local`: JitPack is **not** on the list
of dependency repositories F-Droid allows (only Maven Central, Google Maven,
and OSS Sonatype), so resolving from there is an automatic rejection.

What's **not** a problem:

- Firebase and Crashlytics only live in the `website` and `play` flavors. The
  `fdroid` flavor is clean, which is why the recipe builds `fdroidFull`.
- The `applicationId` is already different from the original
  (`com.arcadesignpro.auroravpn`), a hard requirement for a fork.
- Apache-2.0 license, public repository.

## srclibs

`srclibs:` doesn't accept a bare URL: each entry points to a file inside
`srclibs/` in your `fdroiddata` fork. You need to create two:

`srclibs/usque.yml`
```yaml
RepoType: git
Repo: https://github.com/paulvers-ui/usque.git
```

`srclibs/firestack.yml`
```yaml
RepoType: git
Repo: https://github.com/paulvers-ui/firestack.git
```

They're referenced in the recipe by pinning a commit: `usque@<sha>`,
`firestack@<sha>`. Pin **commits**, not branches — a branch can move, and then
the build stops being reproducible, which is exactly what F-Droid verifies.
For `firestack@<sha>`, the commit has to come from that fork's `n2` branch
(see the warning above); a srclib doesn't pin a branch, only a commit, so
which SHA you pick matters.

**usque doesn't need the NDK.** That fork's `goreleaser.yml` builds with
`CGO_ENABLED=0` — pure Go cross-compiled to `GOOS=android GOARCH=arm64`, no C
compiler. The recipe's `ndk:` step is still needed regardless, because
**firestack does use it** (`gomobile bind` to generate the `.aar`).

## Steps

**1. Tag the release**

```bash
git tag v1.0.0 && git push origin v1.0.0
```

**2. Set up fdroiddata**

```bash
# fork gitlab.com/fdroid/fdroiddata from the web UI, then:
git clone --depth=1 https://gitlab.com/YOUR_ACCOUNT/fdroiddata ~/fdroiddata
cd ~/fdroiddata
git checkout -b com.arcadesignpro.auroravpn
cp <this repo>/fdroid/com.arcadesignpro.auroravpn.yml metadata/
# also create srclibs/usque.yml and srclibs/firestack.yml (above)
```

**3. Fill in the `<PLACEHOLDER>`s** in the `.yml`: versionName, the tag's
commit, the two srclib SHAs, the description, and the NDK version.

Starting points verified at the time this was written (check they're still
each branch's HEAD before using them — this changes with every push):

```
usque    (main): f1dab65
firestack (n2):  0159488
```

Don't copy these blindly: confirm the real commit right before pinning it,
with `git ls-remote https://github.com/paulvers-ui/usque.git main` and the
same for `firestack.git n2`.

**4. Test it on the buildserver before submitting anything**

This step isn't optional. Submitting an MR without having built it will
almost certainly fail and cost you a round trip through the review queue.

```bash
git clone --depth=1 https://gitlab.com/fdroid/fdroidserver ~/fdroidserver
sudo docker run --rm -itu vagrant --entrypoint /bin/bash \
  -v ~/fdroiddata:/build:z \
  -v ~/fdroidserver:/home/vagrant/fdroidserver:Z \
  registry.gitlab.com/fdroid/fdroidserver:buildserver

# inside the container:
. /etc/profile
export PATH="$fdroidserver:$PATH" PYTHONPATH="$fdroidserver"
export JAVA_HOME=$(java -XshowSettings:properties -version 2>&1 > /dev/null \
  | grep 'java.home' | awk -F'=' '{print $2}' | tr -d ' ')
cd /build
fdroid readmeta
fdroid rewritemeta com.arcadesignpro.auroravpn
fdroid lint com.arcadesignpro.auroravpn
fdroid build com.arcadesignpro.auroravpn
```

If something fails, edit the `.yml` and repeat. This is where you'll adjust
`prebuild:` until usque and firestack actually compile — the part that will
take the most effort.

**5. Submit the MR**

```bash
git add metadata/com.arcadesignpro.auroravpn.yml srclibs/usque.yml srclibs/firestack.yml
git commit -m "New app: Rethink Dns Fork"
git push origin com.arcadesignpro.auroravpn
```

MR against `fdroiddata`, titled `New app: Rethink Dns Fork`. Check that the
pipelines pass and that the build one **actually produces an APK**: if it
passes but doesn't produce one, you probably left the build step disabled.

**6. Wait**

After merging, 24 to 48 hours before it shows up in the repository, since
signing the APK requires a human.

## About being a fork

The original is already published, so expect this question: *what does this
fork add?* Have it written out in `Description:`, not improvised on the spot.

It's also worth **notifying the Rethink authors** before submitting. F-Droid
expects the original author to be aware and not opposed.

## Cheaper alternatives

If step 4 gets stuck — which is normal, `gomobile` on the buildserver is
finicky — these don't require building from source:

| option | what it involves |
|---|---|
| **IzzyOnDroid** | third-party F-Droid repo; accepts prebuilt APKs from your GitHub releases. Users add one URL. |
| **Own repo** | `fdroidserver` generates a static repo; host it on GitHub Pages. Full control, no review. |
| **Obtainium** | installs directly from your GitHub releases. Almost no setup. |

None gives you the visibility of the main repository, but all three work
today without rewriting the build.

## Distribution without official F-Droid: GitHub Releases + Obtainium + IzzyOnDroid

If F-Droid's buildserver (200 GB, 8 GB RAM) isn't feasible, this covers
almost the same reach without needing that machine.

### What DOES get automated: build, sign, and publish

Two workflows in `.github/workflows/`:

**`generate-keystore.yml`** — run ONCE, by hand (`Actions` →
`🔑 Generate release keystore` → `Run workflow`, typing `GENERATE`). Creates
a signing key and hands it back as a downloadable artifact (retention set to
1 day on purpose). You need to:

1. Download the run's artifact.
2. Copy the contents of `release.keystore.b64` into the
   `RELEASE_KEYSTORE_BASE64` secret (Settings → Secrets and variables → Actions).
3. Copy the other three values from `secrets-to-save.txt` into
   `RELEASE_KEYSTORE_PASSWORD`, `RELEASE_KEY_ALIAS`, `RELEASE_KEY_PASSWORD`.
4. Delete the run's artifact once the secrets are saved.
5. **Don't run this workflow again** unless you want a brand-new key --
   that breaks in-place updates for anyone who already has the app
   installed, since Android requires the signer to match between versions.

**`release-apk.yml`** — fires on its own, when a `v*` tag is pushed:

```bash
git tag v1.0.1
git push origin v1.0.1
```

Builds `firestack.aar` from `paulvers-ui/firestack@n2` (no JitPack, no 429
risk), assembles the `fdroidFull` APK (no Firebase, no Play Services), signs
it with the keystore secrets, verifies the signature with `apksigner` before
publishing anything, and uploads the result as a GitHub Release with the
`.sha256` attached.

### What does NOT get automated, and why

**Obtainium has no "publish" step on my end.** It's an app each user installs
on their own phone; they point it at `paulvers-ui/rethink-app-masque` as a
"GitHub" source. All Obtainium needs from this repo is well-tagged Releases
with the APK attached -- exactly what `release-apk.yml` already produces. No
extra step needed here.

**IzzyOnDroid is a one-time manual request.** It isn't a push from this repo
-- it's a *Request for Packaging* (or a direct merge request) against
`gitlab.com/IzzySoft/fdroiddata`, reviewed by a person. Once accepted, their
own infrastructure watches this repo's GitHub Releases -- again, what
`release-apk.yml` already produces. Steps:

1. Have at least a couple of Releases published via `release-apk.yml` (so
   there's something real to show).
2. Open an issue at `gitlab.com/fdroid/rfp` (Request for Packaging) or a
   direct MR against `gitlab.com/IzzySoft/fdroiddata`, with:
   - a link to the repo (`https://github.com/paulvers-ui/rethink-app-masque`)
   - what changes from the original Rethink (same as `Description:` in the
     F-Droid `.yml`)
   - confirmation that the Rethink authors were notified
3. Wait for human review -- no fixed SLA.

### Other options with no PC or VPS, for more reach

- **Own F-Droid repo (static)**: `fdroidserver` generates an `index.xml` from
  the APKs `release-apk.yml` already builds; hosted for free on GitHub Pages.
  Users add the repo URL in the F-Droid app. This can also run as a GitHub
  Action, no PC needed.
- **Aptoide / APKPure**: third-party stores, accept direct upload of an
  already-signed APK. Check their terms before uploading anything under a
  FOSS license.
- **Accrescent**: curated repo with stricter security requirements than
  IzzyOnDroid -- worth reviewing their criteria before attempting it.
